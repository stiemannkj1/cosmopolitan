# Plan: luaposix and LuaFileSystem built into Cosmopolitan Lua

Status. This plan has been executed and verified on this checkout. The
working tree now carries the result, uncommitted. See "What was verified"
and "Reverting" at the bottom.

## Goal

One fat APE `lua` binary, x86_64 and aarch64 in the same file, where
`require 'posix'`, `require 'posix.unistd'`, `require 'lfs'` and the rest
behave the way they do on a normal Unix Lua install, so that existing
code can be pasted in and run. Nothing is loaded unless a script asks for
it.

## Why package.preload and not dlopen

Cosmo's Lua still ships `loadlib.c` and a C searcher, but an APE is a
static binary and there are no `.so` files for it to find, so the C
searcher can never succeed. Lua's first searcher, though, is the preload
searcher, which looks up the full dotted module name in
`package.preload` before it ever touches the filesystem. Registering
`luaopen_posix_unistd` there under the key `posix.unistd` makes
`require 'posix.unistd'` resolve to the compiled-in function with no
filesystem access and no loader changes at all. Submodule names map to
`luaopen_` symbol names by turning dots into underscores, which is
exactly how luaposix already names its entry points, so the twenty-eight
C submodules drop straight in.

luaposix is half C and half Lua. The Lua half (`posix/init.lua`,
`posix/_base.lua` and friends) goes into the binary's zip directory as
`.lua/posix/*.lua`, because cosmo's `LUA_PATH_DEFAULT` already starts
with `/zip/.lua/?.lua` and `/zip/.lua/?/init.lua`. So `require 'posix'`
finds the aggregate module in the zip, and that module's own
`require 'posix.unistd'` calls hit preload. No searcher, path or loader
code had to change.

LuaFileSystem has no Lua half, so it is just `luaopen_lfs` in preload
under the name `lfs`.

## What gets added

Two new monorepo packages, `third_party/luaposix` and `third_party/lfs`,
each with vendored upstream sources, a `BUILD.mk`, a `README.cosmo`
recording provenance and every local modification, a license notice
object, and a small hand-written `*preload.c` that registers the modules.
Everything in both directories is generated by `scripts/luaext.py`, so
re-vendoring a newer upstream is one command rather than an afternoon.

Three lines of real integration in existing files. Two `include` lines in
the root `Makefile`, two package names appended to
`THIRD_PARTY_LUA_LUA_DIRECTDEPS` plus the zip objects added to the
`lua.dbg` rule in `third_party/lua/BUILD.mk`, and two calls plus two
includes in `third_party/lua/lua.main.c`. That is the entire diff against
tracked files, fourteen added lines. `linit.c` is untouched on purpose,
so redbean and anything else linking `lua.a` is unaffected.

## The four things that actually had to be ported

Most of luaposix compiles against cosmopolitan libc unmodified. The
headers it wants are all in `libc/isystem`, and the build already passes
`-nostdinc -iquote. -isystem libc/isystem`, so upstream's `<unistd.h>`
and `<sys/stat.h>` includes resolve. LuaFileSystem compiled clean for
both architectures on the first attempt with no source change at all.
Four real problems remained.

**Link-time constants.** Cosmopolitan resolves any constant whose value
differs between the platforms one APE must run on at link time rather
than compile time. `AF_INET6`, `SOL_SOCKET`, `SO_LINGER`, `POLLIN`,
`F_SETLK` and `IPV6_JOIN_GROUP` are `extern const int`, not literals.
That makes them illegal as `switch` case labels and illegal in static
initializers, which produced every one of the nineteen compile errors in
the first build attempt. The fix keeps the original control flow and
moves the dispatch onto compile-time codes. `fcntl.c` switches on a
boolean expression instead of three case labels, `poll.c` fills its
event table in an init function called from `luaopen_posix_poll` instead
of statically, and `sys/socket.c` gets four small mapping functions
(`lposix_afcode`, `lposix_levelcode`, `lposix_sockoptcode`,
`lposix_ipv6optcode`) whose return values become the case labels. This
is the part that will need attention when upstream moves, and the
vendoring script fails loudly rather than silently skipping an edit if
the surrounding code has changed.

**Missing libc entry points.** Cosmopolitan has `mknod` but no `mkfifo`
wrapper, and no `if_nametoindex` at all. Both are supplied as
function-like macros in `third_party/luaposix/cosmo.h`, so
`posix.sys.stat.mkfifo` works and `posix.sys.socket.if_nametoindex`
stays present but returns `nil, "...", ENOSYS` instead of vanishing from
the module table. Separately, `gethostid` is declared by
`libc/runtime/runtime.h` and implemented by nothing, which would have
broken the link, so `HAVE_GETHOSTID` is 0 and the binding is compiled
out the same way it would be on a platform that lacks it.

**No autoconf.** luaposix normally gets `PACKAGE`, `VERSION` and its
`HAVE_*` macros from configure. `cosmo.h` supplies them as a hand-written
config, force-included ahead of every translation unit through
`-include`, because upstream reads those macros before it includes
anything of its own. That header deliberately contains macros only and
includes no cosmopolitan header, because it is parsed before the build's
own `-include libc/integral/normalize.inc` and because `mkdeps` rejects a
third_party header that reaches into `libc/integral`.

**Warnings.** The monorepo builds third_party with `-Wall -Werror`.
Upstream has an unused variable in `fnmatch.c` and `unistd.c` and a
never-null array address test in `sys/socket.c`, so the package turns off
`-Wunused-variable` and `-Waddress` for its own objects rather than
diverging from upstream over cosmetics.

## The one build-system trap

`LINKARGS` in `build/definitions.mk` runs the prerequisite list through
`uniqr`, which reverses it. Whatever is listed last in a `.dbg` rule's
prerequisites ends up first on the link line. Since `luaposix.a` and
`lfs.a` take their `lua_*` symbols from `lua.a`, they have to appear
*before* `lua.a` on the link line, which means they have to be appended
at the *end* of `THIRD_PARTY_LUA_LUA_DIRECTDEPS`. Appending them to the
`lua.dbg` rule directly would push them ahead of `lua.main.o` and the
reference to `luaL_preloadposix` would go unresolved. This cost one
debugging cycle and is worth remembering for any future module.

A smaller ordering constraint follows from it. Because
`THIRD_PARTY_LUA_LUA_DEPS` is computed with `:=` while
`third_party/lua/BUILD.mk` is being read, the two new `BUILD.mk` files
must be included before it, which in turn means they cannot refer to
`$(THIRD_PARTY_LUA_A)`. They name `o/$(MODE)/third_party/lua/lua.a.pkg`
by literal path in their `.pkg` rules instead, which is what the package
symbol checker needs.

## The script

`scripts/luaext.py`, roughly 900 lines, four subcommands, plus the
functional test suite it runs, `scripts/luaext_test.lua`.

```
python3 scripts/luaext.py vendor   # download, verify, port, generate
python3 scripts/luaext.py wire     # idempotent edits to tracked files
python3 scripts/luaext.py build    # both arches, then apelink
python3 scripts/luaext.py test     # native, qemu-aarch64, wine
python3 scripts/luaext.py all      # all four in order
```

`vendor` downloads the pinned upstream tarballs (luaposix 36.3 and
LuaFileSystem 1.8.0), checks their sha256, rewrites every quoted and
angled include into cosmopolitan's repository-root form, applies the
port described above as exact string replacements with expected match
counts, generates `cosmo.h`, the preload registration, the notice
objects, the `README.cosmo` files and both `BUILD.mk` files, and copies
the Lua half into `.lua/posix/`. Tarballs are cached under `o/luaext`.
Every patch asserts its match count, so a future upstream that has moved
the patched code fails the vendor step with the file and the expected
text rather than producing a silently half-ported tree.

`wire` is idempotent and refuses to apply an edit twice.

`build` runs `make MODE=x86_64` and `make MODE=aarch64`, builds
`apelink` and both ape loaders from local source rather than from a
cosmocc release, and fattens the two ELF executables into `o/lua.com`.
Sub-processes run through `bash` on purpose, since Python's `subprocess`
has no ENOEXEC fallback for the APE shell header.

The intended workflow is to run `vendor` once, commit the two generated
`third_party` directories the way cosmo commits all of its vendored
code, and then build with plain `make` from then on. `vendor` is only
re-run to move to a new upstream release.

## What was verified

Full run from a clean tree, `python3 scripts/luaext.py all`, exit 0.

Both architectures build clean, with the only concession being the two
upstream warning categories suppressed for luaposix's own objects. All package
checks pass, including the symbol checker for both new packages and the
strict standalone-header check for the four headers written here.
Upstream's own `lfs.h` is excluded from that check because it names
`lua_State` without including `lua.h`.

`scripts/luaext_test.lua` is a 59-case functional suite, not a smoke
test. It opens and truncates files, locks them with `fcntl` and with
`lfs.lock`, walks directories through both `posix.dirent` and `lfs.dir`,
makes hard and symbolic links, runs a full TCP loopback conversation
(socket, setsockopt, bind, listen, getsockname, connect, accept, send,
recv, getpeername, shutdown), a UDP `sendto` and `recvfrom`, an IPv6
loopback round trip, a `socketpair`, a `SO_RCVTIMEO` timeout, `poll` and
`rpoll`, `fork` with `wait` status decoding and a pipe between parent and
child, `dup2`, signal delivery through `raise`, clocks, `nanosleep`,
`uname`, `getpwuid`, `statvfs`, `getrlimit`, `glob`, `fnmatch`,
`mkdtemp`, `mkstemp`, `realpath`, `setenv`, the whole `lfs` surface
including `lock_dir`, `touch` and `setmode`, the pure-Lua aggregate
`posix` module loaded out of the zip store, and cosmo's own `unix`
module alongside it. A call that fails with an errno meaning the host
does not have the feature is reported as unsupported, anything else is a
failure, and the exit status is nonzero if anything failed.

It passes with zero failures in all three places. On Linux x86_64
against the fat APE, 58 passed and 1 unsupported. On aarch64 under
`qemu-aarch64` against the per-arch binary, the same 58 and 1. On
Windows under `wine` against the fat APE, 53 passed and 6 unsupported.
All twenty-eight C submodules load and expose 150 functions, identically
on Linux and on Windows.

Writing the suite paid for itself twice, because it found two bindings
that were silently missing rather than broken. `posix.stdlib.mkdtemp`
was a stub that answered "not implemented by host C library", because
upstream gates it on `_POSIX_C_SOURCE` and `_XOPEN_SOURCE`, which
cosmopolitan does not set even though it sets `_POSIX_VERSION` to
200809L and has the function. `posix.time.clock_gettime` and
`clock_getres` were absent for the same kind of reason, upstream gating
them on `_POSIX_TIMERS`, which cosmopolitan never defines although it
has both functions and advertises `_POSIX_MONOTONIC_CLOCK`. Both are now
turned on in `cosmo.h` and both work.

Size cost. The x86_64 binary goes from 1,165,948 to 1,359,934 bytes, the
aarch64 one from 1,019,348 to 1,238,550, and the fat APE lands at
2,686,647. Call it 200KB per architecture for both libraries including
the compressed Lua half.

Not verified. Apple Silicon macOS, which is where this repo's earlier
Blink work found real bugs, and which no emulator here can stand in for.
Also not verified, the aarch64 build on real hardware rather than qemu.

## Known gaps

`posix.sys.msg` loads but is empty, since cosmopolitan has no System V
message queues. `posix.sched` loads but is empty, since there is no
`sched_getscheduler` or `sched_setscheduler`. `AF_NETLINK` and
`AF_PACKET` support in `posix.sys.socket` is compiled out, being Linux
only. `gethostid` is absent, and `if_nametoindex` is present but always
fails. `posix.ctype` binds only `isgraph` and `isprint`, which is all
upstream exposes. Everything else in the twenty-eight modules is bound.

`posix.sys.stat.mkfifo` is present but fails with ENOSYS everywhere,
including on Linux, because cosmopolitan's `mknod` refuses `S_IFIFO`
outright (`libc/calls/mknod.c`, "no named pipes!"). It is wired through
`mknod` anyway, so it will start working by itself if that ever changes.
This is the one case where a Unix program's expectations are not met on
Unix.

On Windows the modules all load and the calls that cosmopolitan
polyfills work, while the ones it cannot return the usual
`nil, message, errnum` triple rather than crashing, which is the
behavior asked for. The test run under wine reports six of these.
Symbolic links need a privilege the account does not have, which also
takes out `lfs.lock_dir` since that is a symlink underneath. There is no
group database, so `getgrgid` finds no entry, while `getpwuid` works.
`getrlimit` answers EINVAL, Windows having no rlimits. And `mkfifo`, as
above.

## If upstream moves

Bump the version, URL and sha256 constants at the top of
`scripts/luaext.py` and run `vendor`. If a patched region has changed,
the script stops and names the file and the text it could not find.
Re-read the upstream diff for `fcntl.c`, `poll.c` and `sys/socket.c`
first, since those carry the only behavioral edits. If upstream adds a
submodule, add it to the `MODULES` list, which drives the preload table,
the `BUILD.mk` include list and the symbol declarations all at once.

## Possible follow-ups

Give redbean the same modules by calling the two preload functions from
`tool/net/redbean.c` and adding the packages to its `BUILD.mk`, which is
a five-line change but makes redbean pay the 200KB.

Move the registration into `linit.c` instead, so that everything
embedding `lua.a` gets it. Not done here, because it would force every
`lua.a` consumer to link both libraries.

Add a few more pure-Lua libraries to the zip the same way, since
`.lua/` in the zip store is now a working module path and costs nothing
but the files.

## Reverting

Nothing is committed. To get back to a clean tree,

```
git checkout Makefile third_party/lua/BUILD.mk third_party/lua/lua.main.c
rm -rf third_party/luaposix third_party/lfs scripts o/lua.com
```

To keep it, `git add` the three modified files, the two new
`third_party` directories and `scripts/`.
